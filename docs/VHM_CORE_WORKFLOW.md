# Программный вход Excel и маршрут Core

`src/intake-xlsx.mjs` читает .xlsx через bundled `@oai/artifact-tool`. Мэппинг задаёт исходные листы, физические диапазоны и колонки. Для невыбранных листов сохраняется UNMAPPED_WORKSHEET. Заголовки и итоги исключаются явным диапазоном либо skipRows, исключения попадают в контроль. Ошибка формулы фиксируется как неизвестное значение. Строка с данными без читаемого наименования останавливает импорт для проверки карты.

Пример карты для исследованного листа. Остальные листы требуют своей карты либо проверки замечаний.

```json
{
  "requestId": "request-001",
  "policyVersion": "1.1.0",
  "sheets": [{
    "name": "Лист1",
    "firstRow": 1,
    "lastRow": 139,
    "columns": {"number":"A", "text":"B", "unit":"C", "quantity":"D", "notes":"E"}
  }]
}
```

Получить bundled runtime через Codex Workspace Dependencies. В отдельном writable каталоге создать node_modules junction на bundled packages, скопировать туда `intake.mjs` и `intake-xlsx.mjs` и запустить bundled Node с абсолютными путями:

```sh
node intake-xlsx.mjs input.xlsx mapping.json intake.json
```

Снимок создаётся с запретом перезаписи. Код сохраняет исходные значения до нормализации. Модель, артикул, категория и требования передаются явными полями. Автоматическое извлечение этих данных из свободного текста остаётся открытой частью нормализации.

## Контракт исполнения

`runStrictWorkflow` из `src/workflow.mjs` получает существующую runtime policy, snapshot, A/B/C, лимит вызовов, timeout и candidateDepth. Он вызывает проверенные адаптеры последовательно и передаёт решение существующему `match`. Настройки являются параметрами тестового workflow. Новый draft Policy Engine сам по себе их не активирует.

- `searchMcp({query, city, limit, signal})` и `searchWeb` возвращают массив локаторов карточек. Неподходящие домены исключаются. Прямой lookup использует только явно типизированные поля снимка.
- `verifyMcp({candidates, requirements, city, limit, signal})` возвращает карточки в контракте Matcher со ссылкой на сохранённый ответ и проверяемыми checks. Адаптер отвечает за преобразование сырых полей MCP. Карточка должна соответствовать запрошенному локатору.
- Результат содержит intake, evidence и result. Состояние и документы сохраняет вызывающий процесс. После строгой выдачи result.approvalNeeded содержит ключи строк для согласования. Поиск аналогов остаётся отдельным проходом.
- При неполной технической разметке строка получает уточнение. Ошибка или ограничение источника сохраняется и останавливает его повторные вызовы в текущем запуске. Веб-добор выполняется в пределах бюджета.

## Проверенные результаты

Реальный .xlsx прочитан с отображением 139/139 товарных строк в базовом листе. Исходные номера, текст, количество и единица совпали с ранее сохранённым корпусом. Сохранены замечания о шести остальных листах.

Интеграционный replay использовал 30 ранее размеченных требований и архивные ответы C. Результат сохраняет все 139 строк, 11 EXACT и одно открытое предложение. Для остальных строк статус отражает отсутствие достаточной разметки или доказательств. Четырёхлистный Excel экспортирован и проверен по XML, основной лист содержит 139 записей. Этот результат проверяет соединение программных компонентов на исторических ответах. Он не является новым живым замером качества поиска.

20 автоматических тестов проверяют вход, поиск, восстановление, приёмку и ограничения. Серверный доступ к реальным источникам и полный автоматический разбор Excel до технического ТЗ требуют отдельной интеграции.

Нормализатор автоматически сохраняет `analysis` с текстовыми источниками подсказок. Планировщик использует найденные идентификаторы для текстовых запросов SOURCE_IDENTIFIER_TEXT. Их тип UNKNOWN исключает автоматический точечный lookup. При неполной технической разметке, но обнаруженной категории, workflow выполняет поиск кандидатов и оставляет результат на уточнении. Сверенные обязательные требования по-прежнему нужны для строгой приёмки.
## Типизированная проверка технических характеристик

Workflow поддерживает структурированный тест требования в дополнение к исходному `value`:

```json
{
  "key": "batteryCapacity",
  "value": "4 Ач",
  "field": "Емкость аккумулятора",
  "test": {"kind":"number", "expected":4, "unit":"Ач"}
}
```

Допустимы number, boolean и text. Числовой тест сравнивает точное значение после преобразования совместимых единиц. Поддержаны длина, масса, объём, напряжение, мощность, ёмкость, момент и счётные значения. Допускается только погрешность представления числа с плавающей точкой. Технические допуски и диапазоны требуют отдельного контракта. Для булевого требования expected имеет тип boolean. «Да» и «есть» дают true, «нет» — false. Текст сравнивается после нормализации регистра и пробелов.

Сырые характеристики карточки сопоставляются с полем requirement.field. Отсутствующее поле, несовместимая единица и конфликт значений получают UNKNOWN. Для legacy-требований без структурированного теста сохраняется прежний контракт checks адаптера. Структурированные тесты проходят проверку до сетевых вызовов. Перед передачей в Matcher workflow пересчитывает их по card.characteristics и ссылке на фактический MCP-ответ.

На архивных карточках AEG L1840S, Makita BL1860B и IZELTAS 0345002112 проверены три конкретных свойства: ёмкости 4 и 6 Ач и наличие шарнира. Все три получили PASS с исходными значениями. Это свойство отдельных полей. Остальные требования строк и независимый эталон сохраняют собственные статусы. Локальный журнал `runs/client-pilot/e035/typed-characteristic-replay.json`.

Регрессионный тест передаёт предварительный PASS при фактических 2 Ач против требуемых 4 Ач и подтверждает отказ Matcher в EXACT. Всего 30 тестов прошли. Полное автоматическое составление технических требований из свободного текста остаётся открытым.
## Возобновление заявки и проход аналогов

Строгий workflow возвращает phase STRICT_COMPLETE и digest для политики, нормализованного intake и доказательств. `runAnalogWorkflow({policy, strictRun, permission, connectors, ...limits})` проверяет digest, завершение строгого прохода и разрешённые ключи. Изменение политики или строгих доказательств делает разрешение устаревшим.

```json
{
  "requestId": "request-001",
  "strictDigest": "хеш завершённого строгого прохода",
  "decision": "ALLOW_ANALOG_DISCOVERY",
  "keys": ["ключ разрешённой строки"],
  "by": "manager",
  "at": "2026-11-05T12:00:00Z"
}
```

STRICT_ONLY завершает заявку без новых вызовов. ALLOW_ANALOG_DISCOVERY запускает поиск только по указанным незакрытым строкам, сохраняя полный исходный intake и доказательства строгого этапа. Запрос строится по категории и обязательным незаменяемым параметрам, после чего карточки проходят тот же Matcher. Проверенные отличия должны содержаться в card.differences. Подмена жёсткого параметра блокирует допуск. Для свойства, заранее отмеченного replaceable в требованиях заявки, доказанное отличие может получить DEVIATION и перейти в предложение с отдельным описанием. UNKNOWN остаётся неподтверждённым. Предложенный аналог имеет PENDING до отдельного утверждения конкретного SKU. Свидетельства этапов отмечены STRICT и ANALOG.

`src/run-store.mjs` предоставляет loadRun(directory) и saveRun(directory, run, expectedRevision). Он сохраняет последовательность неизменяемых checkpoint JSON. Перед записью проверяется ожидаемая ревизия и идентификатор заявки. Параллельная или устаревшая запись отклоняется. Запись выполняется через временный файл с flush и rename, поэтому частичный файл не появляется как последняя ревизия. Каталог выбирается внутри игнорируемого runs. Если процесс аварийно завершился с checkpoint-lock, оператор сначала проверяет отсутствие активного процесса и целостность версий, затем решает восстановление блокировки. Инструмент не удаляет такую блокировку автоматически.

Проверены scope разрешения, устаревший digest, завершение STRICT_ONLY, сохранение строгих доказательств, запрет несовместимого аналога, отдельное согласование и конкуренция checkpoint. Это программные интеграционные проверки на контролируемых данных. Живой проход аналогов на клиентской заявке ещё требует отдельного разрешения по её строкам.
## Автоматическая компиляция требований из исходного описания

`src/compile-requirements.mjs` подключён к нормализатору. Если structured requirements уже переданы, их контракт сохраняется. В остальных случаях профиль battery-description-v1 пытается разобрать полное описание отдельного аккумулятора.

Профиль требует одну распознанную марку, идентификаторы, ровно одно напряжение и одну ёмкость. Из исходного текста строятся typed tests. У каждого требования есть source с полем, исходным фрагментом и UTF-16 позициями start/end. Указанные химия, платформа LXT и индикатор заряда становятся обязательными. Тип «аккумулятор» также исключает названный набор или комплект в карточке. Это правило типа товара привязано к исходному слову «Аккумулятор».

Профиль помечается complete только при полном покрытии текста. Неизвестные фразы, отрицания, лишние количества, конфликт марки или дополнительные notes сохраняют review. Категория и бренд автоматически передаются Matcher только при complete. Подсказки поиска при этом доступны и для неполного разбора.

На 139 исходных строках profile matched две позиции, №51 и №126. Обе разобраны полностью. На сохранённых карточках прошли 7/7 и 8/8 проверок соответствующих свойств. Это повторная проверка свойств по архиву. Независимое подтверждение заводского обозначения 632F69-8 сохраняет статус E03.6, отдельный сбор доказательств продолжается.

Интеграционный тест берёт исходный текст без ручных category, brand и requirements, пропускает через нормализатор, VI adapter contract и Matcher. Совпадающий аккумулятор получает EXACT, именованный набор с теми же характеристиками отклоняется. Этот тест использует контролируемый транспорт. Полный живой прогон нового компилятора ещё не измерен. Локальный построчный замер хранится в runs/client-pilot/e035/automatic-battery-compilation.json. Следующие профили требуются для остальных товарных групп.
