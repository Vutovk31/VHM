# Активный мост Codex → VHM Core

`src/run-core.mjs` запускает Core с адаптерами VI MCP и поиска по домену ВИ. Транспорт обслуживает активная авторизованная сессия Codex. Host preflight выполняется по актуальным инструкциям коннектора. Session JSON хранит только `summaryAccepted` и `instructionsVersion`.

```sh
node src/run-core.mjs input.json runs/request-001 C runs/host-session.json
```

Вход содержит requestId, policyVersion, rows и регион заявки. Допустим также уже нормализованный снимок. Технические требования могут быть размечены Codex в рамках того же пользовательского запроса. Неизвестные свойства сохраняют явный статус. Политика runtime остаётся `policy/vi.json`.

## Обслуживание запросов

1. Core сохраняет файлы UUID.request.json в `runs/request-001/host`. Хост читает только запросы текущего запуска с известными UUID.
2. search_products, get_product и get_products передаются соответствующим инструментам подключённого VI MCP. Хост соблюдает ограничения частоты, доступа и preflight.
3. web_search содержит query, начинающийся с site:vseinstrumenti.ru, и limit. Хост выполняет разрешённый веб-поиск и возвращает structuredContent с products (url) и sourceResult для трассировки. Это канал WEB_DOMAIN.
4. Ответ имеет форму `{id, result}`, result — исходный MCP response либо структурированный веб-результат. Transport failure имеет форму `{id, transportError: true}`. Хост сначала пишет временный файл и затем атомарно переименовывает в UUID.response.json. Файлы чужих запросов не обрабатываются.
5. Адаптер сохраняет доказательство до выдачи карточки. Все вызовы выполняются последовательно. Идентификаторы пакетируются одним get_products, URL и коды проверяются по одному. Эти операции входят в бюджет workflow.
6. Core сохраняет immutable revision и result-N.json. Далее выполняется существующий экспорт. Для продолжения по аналогам передай permission.json пятым аргументом после session JSON. Разрешение должно соответствовать digest последнего строгого прохода.

По умолчанию budget времени строки 30000 мс. Переменная VHM_HOST_DEADLINE_MS позволяет явно задать значение в пределах workflow, максимум 60000 мс. В измерение входит ожидание обслуживания хостом. Увеличение лимита фиксируется в протоколе.

## Проверка адаптеров

39 тестов прошли. Проверены ссылка на доказательства, коды ошибок, фильтрация доменов и учётных данных в URL, соответствие запросу ответа, сохраняемые неизвестные поля поставки и точные границы суффикса модели. Поле проверки @title использует исходный заголовок, @siteProductId и @viCode — подтверждённые идентификаторы. Provider characteristics с зарезервированными именами @ исключаются перед добавлением этих полей.

Host может объявить technicalNormalization: true в session JSON. Тогда перед товарным поиском он обслуживает normalize_request по [контракту технического разбора](VHM_TECHNICAL_INTERPRETATION.md). Исходные строки и примечания передаются только локальному Codex. В товарные MCP-запросы и внешний поиск входят полученные товарные признаки.

Необязательный массив reviewedSaleTerms в локальном host-session JSON принимает вручную проверенные условия продажи. У записи обязательны siteProductId, viCode, url, reviewedBy, reviewedAt, size, sourceUnit, orderUnit и целое положительное orderMultiple. Адаптер применяет запись после сохранения доказательства MCP и точного совпадения обоих идентификаторов и URL. Используй актуальную проверку условий перед запуском. Данные клиента, страницы и ответы провайдера не заполняют этот массив автоматически. Региональная поставка проверяется отдельно.

Для крупных ответов Windows хост может вызывать scripts/write-host-response.ps1 по одному фрагменту JSON. Передай каталог host, UUID запроса и Chunk. Первый фрагмент пометь First, последний Last. Сохраняй порядок фрагментов и границы Unicode. При формировании PowerShell литерала экранируй одинарные кавычки, включая типографские. Скрипт проверяет наличие запроса и конверт ответа, затем публикует готовый файл атомарным переименованием. Прерванная передача оставляет staged файл для диагностики. Проверено на ответе размером 119116 байт с кириллицей, кавычками и emoji. Это проверка записи, без вызовов VI.

После завершения выбора режима поиска запиши согласование конкретного предложения командой node src/run-core.mjs --approve output-directory approval.json. Файл содержит revision текущего checkpoint, requestId, key строки, siteProductId предложения, by и at. Команда проверяет текущую ревизию и SKU со статусом PENDING, затем сохраняет новую ревизию. На копии живого контрольного прогона ревизия 3 зафиксировала APPROVED, повтор исходного согласования отклонён. Доставка сохранила NOT_CONFIRMED, закупочная ведомость пуста.
